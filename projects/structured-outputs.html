JSON Schema and constrained decoding

A model asked for JSON can still break the schema your code depends on. Constrained decoding blocks the illegal tokens while the model writes. We reproduced JSONSchemaBench on 9,558 real schemas to see where that works and where it fails.

Follow every schema to the stage where it fails

A single success rate hides where things go wrong. We logged each schema’s outcome at every step.

  1. SchemaTake a JSON Schema from JSONSchemaBench: GitHub, Kubernetes, Snowplow, function calling and more.
  2. CompileTurn it into constraints with Outlines (finite state machine) or Guidance (interleaved generation).
  3. GenerateRun constrained decoding with Llama-3.1-1B-Instruct.
  4. ValidateCheck the output with an external validator, jsonschema.

Feature by feature, support is patchy

Pipeline B, no LLM: the share of test-suite instances each compiled grammar handles correctly.

Outlines is conservative

It handles local checks such as type, enum and default, and drops to zero on global ones like if-then-else, contains and dependentRequired.

Guidance is broader but version-dependent

It scores well on anyOf, items, required and numeric bounds. Several scores moved between the paper’s version and ours.

A positive score can mean nothing

Some test groups contain no valid instance at all, so a dummy that rejects everything scores above zero there. That’s the baseline column.

What limits these numbers

This is a partial reproduction under real constraints, so it measures failure causes better than speed.

60-second compile timeout
Our pipeline gives each schema 60 seconds to compile, which penalises Outlines by design. In production a grammar is usually compiled once and reused, which would remove much of that gap. These numbers describe this setup, not a universal ranking.
A 1B model with a 2,048-token prompt
We used Llama-3.1-1B-Instruct for stability. Large schemas overflowed its prompt window, which alone accounts for 1,355 of the baseline failures.
Shared GPUs
Runs went through Sorbonne’s shared PPTI machines (Tesla V100), often with about 30% of the VRAM free. Out-of-memory crashes and timeouts forced a watchdog to restart runs, and a stable latency benchmark (GCT, TTFT, TPOT) wasn’t possible.
Library versions drift
We used Outlines v0.1.8 and Guidance v0.3. Against the paper’s scores, some features improved quietly and others regressed.
Guidance maxProperties 0.00 → 0.67 Guidance multipleOf 0.20 → 0.60 Guidance exclusiveMinimum 1.00 → 0.00 Guidance pattern 1.00 → 0.67

What we didn’t get to

Directions we documented in the report for future work.

  • Add XGrammar

    Compare all three frameworks on the full benchmark, especially the Hard and Ultra schemas, to see whether its latency advantage holds.

  • Measure latency properly

    Use a dedicated GPU and CUDA events to get reliable compile time, time to first token and time per token against schema complexity.

  • Model why schemas fail

    Describe each schema by size, nesting depth and keywords used, then fit an interpretable model (decision tree, XGBoost) on the outcomes to find which features predict failure.

  • Constrain whole sequences with diffusion

    Token-level masks can’t express rules like uniqueItems or not. Discrete diffusion models refine the full sequence, so those rules could be applied as projections at each step.
