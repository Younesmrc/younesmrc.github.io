Retrieval

BM25, DeepImpact and Guided Traversal on MS MARCO

Learned sparse retrieval ranks better than BM25 but is harder to prune. We reproduced a SIGIR 2022 paper that lets BM25 steer the search while DeepImpact scores the documents it finds, and rebuilt the dual-score index it needs when the original became unavailable.

Let BM25 steer, let DeepImpact judge

DeepImpact ranks better, but its score distribution makes skipping documents less effective. The paper separates the signal that guides the search from the one that scores results.

Upper bounds
Each posting stores a BM25 weight and a DeepImpact weight. For a term, UB_BM25 is its highest BM25 score in the collection, so a document’s best possible score can be bounded without reading all its postings.
MaxScore
Sorts query terms by upper bound. When the bounds of some terms add up to less than the current top-k threshold, those terms become non-essential: alone they can’t get a document into the top-k, so the search stops using them as starting points.
Guided Traversal
Walks the index using BM25 bounds, but scores the documents it visits with DeepImpact. Two heaps: BM25 sets the threshold, DeepImpact ranks the results. A document pruned on BM25 can’t come back, so this is a heuristic for the DeepImpact ranking.
With interpolation
Ranks visited documents by an unweighted sum of BM25 and DeepImpact. There is no BERT call at query time: DeepImpact weights are computed once, at indexing.

Rebuilding the index that disappeared

The paper’s dual-score index couldn’t be recovered, and the README notes this was checked with researchers. So we built our own at MS MARCO scale.

8,841,823passages indexed
≈3.5 Mterms
≈620 Mpostings
≈15 hof GPU compute

The passage count comes from the indexing script. The other three figures are the team’s estimates from the presentation, not from execution logs.

  1. Per documentEach passage is cleaned and tokenized, its terms counted, and a batch goes through DeepImpact. For each kept term the script writes one binary record: term, document, normalized frequency and DeepImpact score. Going document by document avoids rescanning the collection for every term.
  2. Per termThe raw records are loaded, sorted by term then document, grouped into postings lists, and given an IDF. Two compact binary files come out, readable by the C++ engine.

Compact on disk

Both scores are stored as 16-bit floats. A reader finds a term’s list from its offset and length in the dictionary, without scanning the file.

Scoring
k1 = 0.82, b = 0.68 and an average length of 89.3 on the expanded collection. For repeated terms the script keeps the highest DeepImpact score. BM25(t,d) = IDF(t) · tf(k1+1) / [tf + k1(1 − b + b·dl/AVGDL)] IDF(t) = ln[1 + (N − df + 0.5) / (df + 0.5)]
Batches on GPU
512 passages per batch on CUDA when available, with inputs capped at 300 BERT tokens.
Surviving crashes
A checkpoint every four hours stores the last validated document and the raw file size. On restart the raw file is truncated to that point, so a crash doesn’t duplicate postings.
Memory
Postings stream to disk during inference. The final in-place NumPy sort still needs a lot of RAM.

Two bugs that produced plausible numbers

Both gave scores that looked fine and were attached to the wrong things.

Checkpoint layers that didn’t match

The DeepImpact checkpoint named its last layers differently from our model code. Loading with strict=False silently skipped them, so the scoring head was never loaded and every impact was compromised. We remapped the keys and made loading strict.

# checkpoint key  →  local model key
pre_classifier  →  impact_score_encoder.0
classifier      →  impact_score_encoder.3

- load_state_dict(state, strict=False)
+ load_state_dict(state, strict=True)

Word positions are not WordPiece positions

The model’s index() expects positions of BERT sub-tokens. Our first version passed word indices from split(). As soon as one word breaks into several pieces, every later word is shifted. The fix rebuilds positions from each word’s first sub-token, adds the [CLS] offset and respects truncation.

Published figures, not our run

What the paper reports

On MS MARCO Dev, Guided Traversal is about four times faster than DeepImpact (19.5 ms to 4.8 ms) at the same RR@10, and the interpolated version scores higher. Our notebook latencies can’t be compared with these: hardware, software, aggregation and candidate handling differ, and the paper used a 512 GiB server with single-threaded traversal.

What these numbers can’t say

The index and the ranking gain are solid. The speed story belongs to the paper.

No GT or GTI timings from our engine
The C++ engine implements MaxScore, Guided Traversal and the interpolated version, and our presentation described favourable results. The saved outputs don’t include figures that would back a speed-up factor.
Baseline latencies aren’t a speed test
BM25 and DeepImpact both read the same postings in our notebook, so they take about the same time and sit far from the paper’s 5 to 20 ms.
Close to the paper’s index, not identical
Our vocabulary size and postings count differ slightly from the paper’s. Tokenization, normalization or term filtering are the likely causes, but no ablation tested them.
Two different metrics
MRR@10 rewards the rank of the first relevant passage (MS MARCO). NDCG@10 uses graded relevance (TREC). They aren’t comparable to each other.
